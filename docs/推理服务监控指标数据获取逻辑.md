# 推理服务监控指标数据获取逻辑

> 适用范围：`gpu-monitor` 对 vLLM OpenAI 兼容服务的监控。
> 本文按指标逐项说明数据来源、解析规则和计算方式，代码实现以当前仓库为准。

相关实现：

- `src/inference/runtime.js`：定时抓取、探针调度、指标计算与快照组装
- `src/inference/metrics.js`：Prometheus 文本解析、直方图与分位数
- `src/inference/config.js`：服务、探针和并发上限配置
- `src/store/sqlite-store.js`：`inference_sample`、`inference_probe` 落库与查询

## 一、整体采集流程

每个推理服务默认每 15 秒并发请求一次：

| 请求 | 用途 |
| --- | --- |
| `GET {baseUrl}/health` | 服务是否可用、健康检查耗时 |
| `GET {baseUrl}/metrics` | 负载、延迟、吞吐、错误、缓存等统计 |
| `GET {baseUrl}/v1/models` | 模型是否加载、模型名是否匹配 |
| `GET {baseUrl}/version` | vLLM 版本，5 分钟缓存一次，失败保留上次值 |

配置了 `apiKeyEnv` 时，请求会带：

```text
Authorization: Bearer <环境变量中的 key>
```

`/metrics` 的通用解析规则：

- 排除 `*_created`：它是 Counter 创建时间戳，不是计数
- 只保留 `model_name` 等于配置模型、或没有 `model_name` 标签的序列
- 多 engine / 多副本的同名指标相加
- `NaN`、`+Inf`、`-Inf` 记为 `null`
- Counter 两次抓取之间做差分；计数器重置或回绕返回 `null`
- Histogram 用 bucket 差分计算分位数，秒转换为毫秒

首帧没有上一份快照时，部分指标先用累计值兜底；之后只统计两次抓取之间的窗口。**没有新样本时返回 `null`，不能把历史累计值当作当前值。**

## 二、可用性与身份指标

| 指标 | 数据源 | 获取 / 计算逻辑 |
| --- | --- | --- |
| `state` | `/health`、`/v1/models`、`/metrics` | `/health` 非 200 为 `down`；健康但模型不匹配、鉴权失败或 metrics 不可用为 `degraded`；全部正常为 `up`；首帧前为 `unknown` |
| `up` | `/health` | HTTP 200 为 `true`；连接失败或非 200 为 `false` |
| `statusCode` | `/health` | HTTP 状态码 |
| `healthMs` | `/health` | 发起请求到收到响应的耗时，毫秒 |
| `modelsOk` | `/v1/models` | `data[].id` 是否包含配置的 `model`，要求完全相等；401/403 为 `null` |
| `modelsError` | `/v1/models` | 401、列表非法、模型不存在等具体原因 |
| `metricsOk` | `/metrics` | HTTP 200 且至少解析出一条 `vllm:` 指标才为 true |
| `version` | `/version` | 读取 `{"version": ...}`；每 5 分钟刷新，失败沿用上次值 |
| `error` | 上述接口 | 按“健康检查 → 模型列表 → metrics”的顺序取第一条错误 |
| `warning` | `/metrics` | metrics 不可用或格式不兼容时的提示 |

## 三、负载指标

| 指标 | vLLM 原始指标 | 计算方式 |
| --- | --- | --- |
| `running` | `vllm:num_requests_running` | Gauge 直接取，多 engine 相加 |
| `waiting` | `vllm:num_requests_waiting` | Gauge 直接取，多 engine 相加 |
| `waitingCapacity` | `vllm:num_requests_waiting_by_reason{reason="capacity"}` | 按 reason 过滤后求和 |
| `waitingDeferred` | `vllm:num_requests_waiting_by_reason{reason="deferred"}` | 按 reason 过滤后求和 |
| `kvCachePct` | `vllm:kv_cache_usage_perc`，旧别名 `vllm:gpu_cache_usage_perc` | 原值 0~1，乘以 100 转为百分数 |
| `preemptionsTotal` | `vllm:num_preemptions_total`，旧别名 `vllm:num_preemptions` | Counter 累计值 |
| `preemptionsDelta` | 同上 | 本次值减上次值；计数器重置为 null |
| `preemptionsPerMin` | 同上 | `preemptionsDelta / 抓取间隔秒数 × 60` |
| `maxConcurrency` | 不是 vLLM 指标 | 来自 `inference.json` 的可选字段，对应 `--max-num-seqs` |
| `concurrencyPct` | `running` + 配置 | `running / maxConcurrency × 100`；未配置上限为 null |

`waitingCapacity` / `waitingDeferred` 在较老版本（如 vLLM 0.28）可能不存在，页面显示 `--`。

## 四、延迟指标

### 4.1 平均值

| 指标 | 原始指标 | 计算方式 |
| --- | --- | --- |
| `ttftAvgMs` | `vllm:time_to_first_token_seconds_sum/_count` | 首帧 `sum/count × 1000`；之后用两次抓取的差分相除；没有新请求为 null |
| `e2eAvgMs` | `vllm:e2e_request_latency_seconds_sum/_count` | 同上 |

### 4.2 P95 分位数

| 指标 | Histogram 基础名 | 计算方式 |
| --- | --- | --- |
| `ttftP95Ms` | `vllm:time_to_first_token_seconds` | bucket 差分后取 P95，桶间线性插值，秒转毫秒 |
| `e2eP95Ms` | `vllm:e2e_request_latency_seconds` | 同上 |
| `itlP95Ms` | `vllm:inter_token_latency_seconds` | 同上 |
| `queueP95Ms` | `vllm:request_queue_time_seconds` | 同上 |
| `prefillP95Ms` | `vllm:request_prefill_time_seconds` | 同上 |
| `decodeP95Ms` | `vllm:request_decode_time_seconds` | 同上 |

分位数算法：

1. 取当前抓取和上一次抓取的同名 `_bucket`。
2. 相同 `le` 的 bucket 做差分，得到本轮窗口直方图。
3. 找到累计计数达到 `P95 × 总数` 的 bucket。
4. 在前一个桶和当前桶之间线性插值。
5. 结果乘以 1000，单位毫秒。

如果本轮 `_count` 差分为 0，P95 返回 `null`。

## 五、吞吐指标

| 指标 | 原始指标 | 计算方式 |
| --- | --- | --- |
| `promptTokensTotal` | `vllm:prompt_tokens_total`，旧别名 `vllm:prompt_tokens` | Counter 累计值 |
| `generationTokensTotal` | `vllm:generation_tokens_total`，旧别名 `vllm:generation_tokens` | Counter 累计值 |
| `promptTokensPerSec` | prompt Counter | `(本次 − 上次) / 间隔秒数` |
| `generationTokensPerSec` | generation Counter | `(本次 − 上次) / 间隔秒数` |
| `tokensPerSec` | generation Counter | 兼容旧字段，等于 `generationTokensPerSec` |
| `requestsPerMin` | `vllm:request_success_total` | `(本次请求总数 − 上次) / 间隔秒数 × 60` |
| `stepTokensAvg` | `vllm:iteration_tokens_total` 的 `_sum/_count` | 差分后 `sum/count`，表示每个引擎 step 平均处理多少 token |

`stepTokensAvg` 依赖 vLLM 暴露 `iteration_tokens_total` 直方图；没有该指标的版本显示 `--`。

## 六、质量指标

| 指标 | 原始指标 | 计算方式 |
| --- | --- | --- |
| `requestSuccessTotal` | `vllm:request_success_total` | 汇总所有 `finished_reason` 的累计请求数 |
| `requestErrorTotal` | 同上，`finished_reason="error"` | 只取错误结束的累计值 |
| `requestAbortTotal` | 同上，`finished_reason="abort"` | 只取客户端中断的累计值 |
| `errorRatePct` | 请求总数 + error | `errorDelta / requestDelta × 100` |
| `abortRatePct` | 请求总数 + abort | `abortDelta / requestDelta × 100` |
| `prefixCacheHits` | `vllm:prefix_cache_hits_total`，旧别名不带 `_total` | Counter 累计值 |
| `prefixCacheQueries` | `vllm:prefix_cache_queries_total`，旧别名不带 `_total` | Counter 累计值 |
| `cacheHitPct` | 上面两个 Counter | `hitsDelta / queriesDelta × 100`；queries 为 0 或指标不存在为 null |

`requestDelta` 包含 stop、length、abort、error 等所有结束原因，所以错误率和中断率以“完成的请求”为分母。

## 七、主动探针指标

### 7.1 单次探针记录

探针不是从 `/metrics` 读取，而是实际发请求：

| 服务类型 | 探针端点 | 请求 |
| --- | --- | --- |
| `chat` | `POST /v1/chat/completions` | 小 prompt，默认 `max_tokens=32`，流式 |
| `completions` | `POST /v1/completions` | 小 prompt，流式 |
| `embeddings` | `POST /v1/embeddings` | `input: "ping"` |
| `rerank` | `POST /v1/rerank` | `query: "ping"`，`documents: ["pong"]` |

每次探针记录字段：

| 字段 | 来源 |
| --- | --- |
| `ts` | 探针开始时间 |
| `serviceId` / `kind` | 配置 |
| `ok` | HTTP 200 且响应结构有效 |
| `skipped` | 因启动宽限期、服务不可用或 `idleOnly` 忙碌而没有真正发请求 |
| `status` | HTTP 状态码 |
| `cold` | 本轮是冷启动请求还是热态请求 |
| `ttftMs` | 流式响应中第一个 `delta.content`、`delta.reasoning` 或 `delta.reasoning_content` 非空的时间；兼容 vLLM 与 llama.cpp reasoning 模型 |
| `e2eMs` | 从发请求到流结束的总耗时 |
| `outputTokens` | 优先取 `usage.completion_tokens`；没有 usage 时用流式内容 chunk 数近似 |
| `tokensPerSec` | `outputTokens / (e2e − ttft)`；非流式为 `outputTokens / e2e` |
| `error` | 超时、HTTP 错误、鉴权失败、响应结构错误等 |

chat/completions 默认 `warmup: true`：

1. 第一次请求记为 `cold=true`
2. 第一次成功后紧接着第二次，记为 `cold=false`

embedding / rerank 只发一次，没有冷热区分。

### 7.2 卡片上的探针统计

| 指标 | 计算方式 |
| --- | --- |
| `probeStats.samples` | 最近最多 50 次非跳过探针结果，内存中维护，重启清零 |
| `probeStats.successPct` | `成功次数 / samples × 100` |
| `probeStats.coldWarmRatio` | 最近一次冷 TTFT / 最近一次热 TTFT；两者都有值才计算 |
| 最近探针时间 | 前端用 `probe.at` 计算“几秒/几分钟前” |
| 探针状态 | 通过 / 失败 / 跳过，来自最近一次探针结果 |

`probeStats` 只在内存里，不单独落库；探针明细会写入 `inference_probe`，可以事后重算。

## 九、数据落库与查询

### `inference_sample`

每个服务每轮抓取一行，包含：

- 可用性：`state`、`up`、`models_ok`、`metrics_ok`
- 负载：`running`、`waiting`、`waiting_capacity`、`waiting_deferred`、`kv_cache_pct`、`preemptions_*`
- 延迟：`ttft_avg_ms`、`e2e_avg_ms`、`ttft_p95_ms`、`e2e_p95_ms`、`itl_p95_ms`、`queue_p95_ms`、`prefill_p95_ms`、`decode_p95_ms`
- 吞吐：`prompt_tokens_per_sec`、`generation_tokens_per_sec`、`requests_per_min`、`step_tokens_avg`
- 质量：`error_rate_pct`、`abort_rate_pct`、`cache_hit_pct`
- 配置：`max_concurrency`、`concurrency_pct`

### `inference_probe`

每次探针一行，包含：

- `service_id`、`kind`
- `ok`、`skipped`、`status`、`cold`
- `ttft_ms`、`e2e_ms`、`output_tokens`、`tokens_per_sec`
- `error`

所有取不到的指标都写入 `NULL`，不会写 0。`/api/inference/history` 和 `/api/inference/probes` 再按时间范围、服务、结果过滤查询；导出 CSV 也直接来自这两张表。

## 十、缺失数据的处理原则

- 指标版本不支持：显示 `--`，不填 0
- 本轮没有新请求：P95、TTFT、E2E 等窗口指标为 null
- 服务不可用：保留 `up=false` 和错误原因，不伪造业务指标
- 探针跳过：写入 `skipped=1`，不计入成功率，也不视为失败
- 计数器重置：差分返回 null，等待下一轮恢复
